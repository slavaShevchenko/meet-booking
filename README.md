# Бронирование переговорной комнаты

Интерфейс бронирования переговорной комнаты на рабочий день 09:00–18:00.  
Пользователь видит окно из трёх дней, начиная с сегодняшнего, может создавать, редактировать и удалять брони, а также получать корректную обработку конфликтов при пересечении слотов.

Проект реализован с эмуляцией сервера, строгим разделением слоёв и чистыми функциями бизнес-логики.

---

## Стек

- **Фреймворк:** Vue 3, Composition API, `<script setup lang="ts">`
- **Сборка:** Vite
- **Язык:** TypeScript (strict, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`)
- **Состояние:** `createGlobalState` и `useStorage` из `@vueuse/core` (без Vuex/Pinia)
- **Линтеры:** ESLint + Prettier (стиль: без точек с запятой, одинарные кавычки)

## Особенности реализации

### Архитектура

Код разделён на слои с единственной ответственностью. Компоненты не содержат бизнес-логики и не обращаются к API напрямую.

| Слой | Назначение |
|---|---|
| `types/` | Все типы данных: сущности, контракты, ошибки, модели валидации и представления |
| `config/` | Единая точка конфигурации: рабочие часы, длительности, шаг сетки, геометрия, латентность мока |
| `lib/` | Чистые функции без побочных эффектов: работа со временем, датами, пересечениями, валидация |
| `api/` | Эмуляция сервера и клиентский интерфейс. Единственная точка взаимодействия с данными для UI |
| `store/` | Глобальное состояние приложения: брони по датам, флаги загрузки и ошибок, состояние формы |
| `composables/` | Логика компонентов: навигация по датам, загрузка и изменение броней, форма, построение сетки |
| `components/` | Презентационные компоненты: сетка, форма, элементы интерфейса, навигация |

### Управление состоянием

Использован `createGlobalState` из `@vueuse/core` вместо Vuex/Pinia по следующим причинам:

- Приложение небольшое, не нужен полноценный стор с модулями и плагинами
- `createGlobalState` даёт реактивное состояние, общее для всех компонентов без дополнительной настройки
- В `useStorage` сохраняется только `anchorDate` (выбранная дата навигации), так как список броней — это данные сервера, источник истины для них — API, а не localStorage

### Эмуляция сервера

Весь сервер реализован в `src/api/` как in-memory решение:

- `mockStore` хранит данные и детерминированный сид с занятыми слотами
- `mockServer` добавляет задержку 300–600 мс, серверную валидацию и ответы 409 / 400 / 404
- `client` предоставляет интерфейс `BookingApi` — единственная точка для UI, которую легко заменить на реальный `fetch`

#### Эмуляция «гонки»

Сервер может вернуть конфликт (409), даже если по данным `GET` слот казался свободным. Это ожидаемое поведение, а не баг.

- Завтрашний слот 12:00–13:00 выглядит свободным в списке
- При попытке создать бронь сервер возвращает 409 с `conflictingBookingId`
- Список броней автоматически перечитывается, в сетке появляется «бронь коллеги»
- Форма остаётся открытой с введёнными пользователем данными

Управление эмуляцией из консоли:

```js
mockServer.injectFailure('network') // симуляция сетевой ошибки или 500
mockServer.reset()                  // сброс данных к исходному сиду
```

## Бизнес-правила

Все правила реализованы в чистых функциях `lib/validation.ts` и продублированы на стороне «сервера».

1. Время начала и окончания в пределах 09:00–18:00
2. `start < end`
3. Минимальная длительность — 30 минут
4. Максимальная длительность — 2 часа
5. Бронирования не пересекаются. Касание границ допустимо: 10:00–11:00 и 11:00–12:00
6. Прошедшее время недоступно: для сегодняшней даты прошедшие слоты заблокированы, для прошедших дат создание невозможно
7. При редактировании бронь не конфликтует сама с собой

```bash
npm install

```

Приложение будет доступно по адресу из вывода терминала (обычно `http://localhost:5173`).
