## mockServer

Сетевой слой отделён от UI и легко заменяем на реальный. UI обращается только
через `api/client.ts`. Контракт:

GET    /api/bookings?date=YYYY-MM-DD   -> Booking[]
POST   /api/bookings                   -> Booking        (body: BookingDraft)
PATCH  /api/bookings/:id               -> Booking        (body: Partial<BookingDraft>)
DELETE /api/bookings/:id               -> 204

Тип:

ts
type Booking = {
  id: string
  date: string // YYYY-MM-DD
  start: string // HH:mm
  end: string // HH:mm
  title?: string
}

- `mockServer` хранит данные в памяти (`mockStore`), отвечает с искусственной задержкой (~300–600 мс).
- Сервер сам валидирует все бизнес-правила и при пересечении возвращает `409 Conflict`
  с понятным payload (`{ error: 'CONFLICT', message, conflictingBookingId? }`).
- Добавь детерминированный сид: несколько занятых слотов на сегодня/завтра, чтобы было видно существующие брони и конфликт при попытке наложить.
- Реализуй гонку: даже если UI считал слот свободным, сервер может вернуть 409.
  Сделай так, чтобы это было воспроизводимо (например, один призрачный слот или
  вероятность конфликта), и UI обязан это корректно обработать.
- Ошибки пробрасывай типизированно (`ApiError` с `status`), чтобы UI различал 409 / 400 / 500 / network.

## State management

- `createGlobalState`-стор хранит: брони по датам (`Record<date, Booking[]>`),
  флаги `loading`, `error`, состояние открытой формы (create/edit, черновик, id).
- Peristence в `localStorage` — опционально для списка броней (лучше НЕ персистить
  серверные данные, т.к. источник истины — mockServer; персистить можно только UI-предпочтения, например выбранную дату). Обоснуй выбор в комментарии.
- `useBookings` — вся работа с API: загрузка по дате, create/update/delete, обработка loading/error/409.
- Компоненты не импортируют `api/client` напрямую — только через composables.

## UI: навигация по дням и отображение

- При открытии пользователь видит **окно из 3 дней**, начиная с сегодняшнего (`VISIBLE_DAYS = 3`).
- Две стрелки (prev / next) листают окно по одному дню.
  - `next` — всегда активна.
  - `prev` — disabled, когда первый видимый день == сегодня (в прошлое не уходим).
  - Прошедшие дни (до today) создавать бронь не дают (правило 6).
- Формат отображения — сетка/таймлайн дня с колонками на каждый видимый день;
  существующие брони — карточками, positioned по времени. Свободное время кликабельно ->
  открыть форму создания с предзаполненным start.
- Клик по брони -> режим редактирования; удаление — с подтверждением.

## Требования к качеству кода

- Все функции типизированы, никаких `any` без крайней необходимости (и с комментарием).
- Чистые функции в `lib/` — без побочных эффектов, легко тестируемые.
- Никакой бизнес-логики и вычислений времени прямо в шаблонах `.vue` — выноси в computed/composables/lib.
- Единая точка конфигурации (`config/schedule.ts`) — никаких магических чисел/строк по коду.
- Осмысленные имена, короткие функции, отсутствие дублирования.
- Комментарии — только там, где объясняется «почему» (нетривиальная логика, эмуляция конфликта).

## Чек-лист приёмки (проверь каждый пункт)

- [ ] Видны 3 дня от сегодня; стрелки листают по дню; prev disabled на сегодня.
- [ ] Создание брони: валидация всех правил 1–6, ошибки подсвечены по полям.
- [ ] Пересечение блокируется (в т.ч. на «сервере» -> 409), касание границ разрешено.
- [ ] Минимальная 30 мин и максимальная 120 мин длительности enforced.
- [ ] Прошедшее время сегодня и прошедшие даты недоступны для создания.
- [ ] Редактирование: своя бронь не конфликтует сама с собой; данные сохраняются.
- [ ] Удаление работает (с подтверждением).
- [ ] Серверный 409 при «свободном по UI» слоте: сообщение показано, список обновлён, введённые данные в форме НЕ потеряны.
- [ ] Все состояния UI присутствуют: loading, empty, error, submitting.
- [ ] API-слой изолирован, заменяем на реальный без правок UI.
- [ ] Адаптивность и базовая доступность соблюдены.
